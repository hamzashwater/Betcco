# Monitoring and alert contract

## Scope and evidence boundary

This document defines the repository-controlled signals and provider-neutral alert recommendations for ASUS-10E2. The application emits health responses and stable structured log events; it does not configure a metrics/log collector, alert receiver, monitoring vendor, pager, on-call rota, severity policy, or response SLA.

**Repository-controlled foundation:** event names/IDs, safe log fields, health endpoint semantics, persistent operational states, recommended thresholds, and incident procedures.

**External production evidence still required:** deployed collection and routing, alert ownership and acknowledgement, approved thresholds/severity/SLA, staging and production alert delivery, and escalation records. Thresholds below are **repository recommendations**, not deployed or owner-approved production alerts.

The event ID and structured fields form a provider-neutral contract. Consumers should match the numeric ID or exact event name, not parse rendered prose. Never forward secrets, access tokens, cookies, connection strings, SMTP/S3 credentials, private upload data, raw provider request/response bodies, or unnecessary personal data into logs or alert payloads. Treat provider references as sensitive unless an existing approved workflow specifically needs them.

## Staging exercises

Before relying on an external alert, operators should cause a controlled failure in staging, verify the event or health transition reaches the configured receiver, acknowledge it, follow the linked runbook, restore the dependency, and record timestamps and outcome. Use synthetic accounts, files and transactions only. Do not use live payment credentials or create a production incident from a synthetic alert. These exercises are recommendations; no receiver or delivery has been demonstrated by this repository.
