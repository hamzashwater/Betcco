# PayTabs full-refund reference recovery — ASUS-09B

## RF2 recovery and Finance reconciliation addendum — 2026-09-29

RF2 uses the existing `RefundService` provider verification, serializable internal accounting, and RF1 grant/credit disposition. A `ProviderProcessing` refund with no saved provider reference now uses the same conservative cart discovery as `ProviderResultUnknown`; it never resends refund creation. A provider result with mismatched identity or profile cannot bind a reference or become a definite failure. A verified refund whose accounting cannot complete opens or retains a review case; successful internal finalization or trusted definite failure resolves active linked cases. Repeated verification uses the same Refund ID and existing financial uniqueness and transaction boundaries.

The Finance reconciliation endpoint delegates to `ProviderReconciliationService`. Requery invokes the existing refund workflow and returns current Refund/Payment state; cases record a requery audit and last-check time. Expected and observed provider amounts/currencies are distinguished through immutable case evidence and structured audit observations, including mismatch categories and reference conflicts. A persisted `ProviderVerified` refund with incomplete accounting exposes the specific review code while retaining its financial state. Manual `ProviderConfirmed` is rejected because typed text is not provider evidence. `ReviewedNoFinancialAction` cannot close a financially unresolved refund; `EscalatedToFinance` requires a note and records external handling without financial mutation. Existing historical resolution codes remain readable. Case snapshot evidence is immutable; current statuses and recovery state are projected from the linked Refund/Payment. No schema migration is required.

Local PostgreSQL tests cover missing-reference recovery, Finance requery, concurrent requery, accounting replay, and unused included-credit revocation exactly once. The suspected unused-credit defect was **NOT REPRODUCED — PROTECTED BY TEST**. Live PayTabs Test/Sandbox, production behavior, provider-side idempotency, and external manual reconciliation remain unverified.

**Decision (2026-09-27):** A timed-out refund creation with no returned PayTabs reference remains `ProviderResultUnknown`. Finance Admin may use the existing refund verification action to discover a reference, then verify it independently. No refund-create retry is permitted: the timed-out request may already have created a provider refund.

## Discovery and trust boundary

BETCCO generated `PayTabsPaymentProvider.RefundCartId(refund.Id)` when it sent the original full-refund request. Recovery queries PayTabs with this server-owned cart ID and the configured profile ID. The [official query documentation](https://support.paytabs.com/en/support/solutions/articles/60000806381-7-1-hosted-payment-page-apis-query-transaction) says a cart-ID query returns an array of matching transactions. It is discovery only; it never directly finalizes accounting.

The adapter parses every array item through the existing ASUS-09A refund transaction classifier and retains the optional `previous_tran_ref`. PayTabs [documents that reference](https://docs.paytabs.com/manuals/PT-API-Endpoints/Integration-Types-Manuals/Request-Response-Parameters/Response-Previous-Tran-Ref/) as a link to the original transaction, while marking the field optional. Automatic reference binding therefore requires **exactly one** candidate with the configured profile, PayTabs provider, server-generated refund cart ID, refund transaction type, original refund currency and amount, a nonempty refund reference, and a `previous_tran_ref` exactly equal to the original Payment's provider reference. Missing linkage is review-required; no linkage is inferred.

An empty array remains recoverable (`PAYTABS_REFUND_RECOVERY_NOT_FOUND`) because provider visibility timing is unverified. Zero trusted candidates return `PAYTABS_REFUND_RECOVERY_UNVERIFIED`; multiple trusted candidates return `PAYTABS_REFUND_RECOVERY_AMBIGUOUS`. A reference already bound to another PayTabs Refund returns `PAYTABS_REFUND_REFERENCE_CONFLICT`. Transport, HTTP, or payload failure returns `PAYTABS_REFUND_RECOVERY_RESULT_UNKNOWN`. None of these outcomes proves provider failure or resends the refund. Attempts and successful reference binding have audit events without credentials or full provider payloads.

After a single trusted reference is persisted, the service calls the existing reference-based `VerifyPayTabsRefundAsync` path. A `P`, `H`, `V`, or unknown result remains non-final with the recovered reference available for another query. A trusted `A` may pass the existing provider verification and full-refund accounting checks; a trusted `D`, `E`, or `X` may become `ProviderFailed` without accounting. Replays of already recorded refunds return the existing idempotent result. Reference binding and final verification use PostgreSQL serializable transactions with bounded conflict retries; the same endpoint remains restricted to Finance Admin.

This change adds no schema or migration and does not change the provider-agnostic partial-accounting calculation or course-access policy. PayTabs partial-refund execution remains disabled (`PARTIAL_REFUND_PROVIDER_EXECUTION_DISABLED`); ASUS-08C2 remains NO-GO. PayTabs Test/Sandbox behavior, cart-query visibility after timeout, presence of `previous_tran_ref` on real query results, and provider-side idempotency have **not** been verified. A missing linkage or prolonged not-found result still needs manual provider reconciliation.
