## Monetary field audit

| Stored group | Inspected fields | EF/PostgreSQL definition and code contract |
| --- | --- | --- |
| `Payment` | `Subtotal`, `Discount`, `Tax`, `Total` | `numeric` without explicit `(precision, scale)` in the snapshot/migrations. `CommerceService` computes several components at three places but does not validate the whole snapshot to that scale. |
| `Refund` | `Amount` | `numeric` without explicit scale. `RefundService.IsValidRequest` checks positive amount and other request fields, not representability at three decimals. PayTabs initiation currently generates only full `Payment.Total` refunds. |
| `CourseSaleAllocation` | `GrossAmount`, `DiscountAllocated`, `NetAmount`, `PlatformCommission`, `TeacherEarning` | `numeric` without explicit scale. `RecordCourseRevenueSplitAsync` rounds nonfinal proportional net and platform commission to three decimals; final net and teacher earning are residuals. | `WalletTransaction`, `LedgerEntry` | `Amount` | `numeric` without explicit scale. `WalletService` rounds wallet request amounts, while Commerce/Refund service writes derived decimal values directly. Ledger validates positive entries and balance, not scale. |
| `Invoice`, `CreditNote` | Invoice `Subtotal`, `Discount`, `Tax`, `Total`; CreditNote `Amount` | `numeric` without explicit scale. `CommercialDocumentService` copies trusted Payment/Refund amounts; it does not establish a common JOD scale. |
| PayTabs JSON | `cart_amount` | `JsonContent.Create` serializes the supplied .NET `decimal` as a JSON number. The four three-place cases and the `1.2345` case prove local exact token behavior. |

**CURRENT CODE CONVENTION:** several sale and wallet calculations use three decimal places. **THREE-DECIMAL ENFORCED CONTRACT: NO.** No centralized money-unit rule, shared representability validator, or restrictive database scale was found for the listed fields. No binary floating-point conversion appears in the audited PayTabs refund amount path; the contract and parser use `decimal`.

## Recommendation for ASUS-08A2 and readiness

**Engineering recommendation, not implemented:** centralize a JOD `0.001` unit using `decimal` only; use an explicit, consistent `MidpointRounding.AwayFromZero` rule for *derived* internal amounts; require external/customer refund inputs and persisted original snapshots to already be exactly representable, rejecting extra precision instead of silently rounding an external refund. Audit the existing percentage-coupon default midpoint behavior before changing it. Verify the provider's actual accepted amount precision and query semantics before applying the rule to provider execution. No database migration or blanket historical conversion is authorized here.

| ASUS-08B partial internal accounting | **NO** | A2 contract, cumulative allocation implementation, tax-only ledger case, CreditNote gate, and concurrency/idempotency evidence remain unresolved. |
| ASUS-08C PayTabs partial execution | **NO** | Live/sandbox partial settlement, accepted scale, and timeout/deduplication contract are unverified. The current `PARTIAL_REFUND_PROVIDER_EXECUTION_DISABLED` and `PARTIAL_REFUND_ALLOCATION_POLICY_REQUIRED` guards remain intact. |

No runtime code, database schema, migration, or Resit file is changed by ASUS-08A1. This report distinguishes local tests and simulated HTTP from real PayTabs behavior; it does not authorize partial execution.
