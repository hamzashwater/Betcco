# Course Payment Partial Refund Accounting Policy

## Status and boundary

**PROPOSED INTERNAL POLICY — REVIEW REQUIRED.** ASUS-07 is documentation only. None of the partial financial, provider, document, or status rules below is implemented or enabled. The previously approved product rule is narrower: a partial refund is a **price concession** with no automatic course-access or included-credit change (`docs/decisions/refund-course-access-policy.md`, “Partial Refund Policy”). This proposal covers only partial refunds of course and course-cart Payments; the verified checkout purpose in current code is `CourseCart` (`CommerceService.CreateCourseCheckoutAsync`). Any legacy course purpose needs explicit evidence before inclusion. It defines no policy for Evaluation, Resit, Retake, Payout, Subscription, Membership, Package, or AI/RAG payments. Resit Commerce remains a separate ASUS/LENOVO handoff.

This document describes **internal engineering allocation**, not statutory Jordan tax treatment, JoFotara submission, a tax-liability adjustment, or a complete general ledger. Tax must never be treated as teacher or platform revenue. The existing approved full-refund snapshot principle in `docs/decisions/taxed-full-refund-accounting-policy.md` remains the baseline; that document's historical status and reproduction narrative predate the full-refund changes now on `main` and must not be read as a current runtime audit.

## Proposed monetary and tax rule

Use only persisted original Payment, Refund, and CourseSaleAllocation snapshots. Never reconstruct a refund from today's course prices, `SalesTaxPercent`, coupon settings, or commission percentage. Apply this model only after validating a course/course-cart Payment and a trusted refund source:

```text
originalTotal            = Payment.Total
originalTax              = Payment.Tax
originalRevenue          = originalTotal - originalTax
previouslyRefunded       = SUM(Amount of this Payment's already InternallyRecorded Refunds)
remainingRefundable      = originalTotal - previouslyRefunded
partialRefundAmount      = current Refund.Amount
cumulativeRefundedAmount = previouslyRefunded + partialRefundAmount
```

Require `Payment.Purpose == "CourseCart"` for the verified current flow, `originalTotal > 0`, `0 <= originalTax <= originalTotal`, matching nonempty currencies, `0 < partialRefundAmount <= remainingRefundable`, and `cumulativeRefundedAmount <= originalTotal`. A zero-total Payment cannot use the ratio: stop for review, do not divide by zero or manufacture a tax amount. Before finalization, resolve any provider-processing/unknown/verified Refund whose external effect may already have occurred; it cannot be treated as harmless merely because it is not `InternallyRecorded`.

For the current refund, compute the **cumulative** tax target from the original tax snapshot, then take the difference from tax already represented by previously finalized refunds:

```text
cumulativeTaxTarget = ROUND_MONEY(originalTax * cumulativeRefundedAmount / originalTotal)
taxComponent        = cumulativeTaxTarget - SUM(previous finalized tax components)
revenueComponent    = partialRefundAmount - taxComponent
cumulativeRevenue   = cumulativeRefundedAmount - cumulativeTaxTarget
```

At a cumulative full refund, set the target to **exactly** `originalTax` and the revenue target to **exactly** `originalRevenue`. Validate `0 <= taxComponent <= partialRefundAmount`, `0 < revenueComponent <= originalRevenue - previouslyReversedRevenue` for a finalizable partial under the existing ledger guard, and that cumulative tax/revenue equal the customer refund total. A tax-only increment with `revenueComponent == 0` must stop for review until a separately designed accounting path exists. Previous tax components can be checked as each prior `Refund.Amount` minus that Refund's linked revenue-ledger reversal; if this evidence is missing or inconsistent, stop for review. The internal ledger remains revenue-only; this split is reconciliation evidence, not a statutory tax entry.

The cumulative method bases every step on one immutable snapshot, prevents repeated independent rounding drift, and converges to the original tax and total on a complete refund. It does not declare any statutory Jordan or JoFotara outcome.

## Proposed course and revenue-share allocation

Require the original allocations to be present, all in the Payment currency, nonnegative, with `SUM(NetAmount) == originalRevenue` and each `PlatformCommission + TeacherEarning == NetAmount`. Use **all** original allocations. An amount alone does not identify a customer's intended course; a course-line refund is outside this policy.

Allocate the **cumulative revenue target** across original `CourseSaleAllocation.NetAmount` weights, then book only each allocation's increase over its previously finalized reversal. Use a fixed minor monetary unit determined by the centralized rounding rule below. The deterministic residual procedure is:

1. Sort allocations by `CourseId`, then `CourseSaleAllocation.Id` ascending. Convert validated original amounts and cumulative targets to integer minor units.
2. Starting from the already finalized cumulative assignments, for each additional revenue minor unit, consider allocations still below their original `NetAmount`. Give the unit to the allocation with the largest deficit `n * originalNetUnits / originalRevenueUnits - assignedUnits`, where `n` is the next cumulative revenue-unit count. Break equal deficits by the stable order above.
3. The last residual unit therefore goes to the eligible allocation with the largest deficit, with the stable order breaking a tie. Never assign below zero or above original capacity. Rebuild/reconcile previous assignments from immutable prior refund ledger evidence before continuing. A full cumulative refund must assign every allocation exactly its original `NetAmount`.

For each allocation's cumulative revenue reversal, apply the same monotone unit-by-unit deficit rule to its **original persisted** `PlatformCommission` and `TeacherEarning` weights, with platform first on an exact tie. Book only the current increments. The two components must sum to that allocation's current revenue reversal, never exceed their original amounts cumulatively, and equal the original persisted split at a complete refund. Do not read the current commission setting. If the original allocation or split is inconsistent, stop rather than repair it by inference. An allocation with zero original `NetAmount` receives no revenue/share reversal. A Payment with zero original revenue needs a separate explicitly tested tax-only design; ASUS-08 must stop it for review under this proposal.

This monotone cumulative procedure is chosen to avoid a rounded independent-per-refund split or a recomputed largest-remainder split that can decrease a previously assigned course. ASUS-08 may implement an equivalent efficient algorithm only if it proves the same deterministic targets, caps, ties, and full-refund convergence.

## Rounding and precision gate

**Observed convention, not yet a formal currency contract:** current course sale/tax/wallet code uses decimal arithmetic and three decimal places, generally `MidpointRounding.AwayFromZero`. Proposed internal JOD calculations use a `0.001` unit and `AwayFromZero` for the cumulative tax target **only if** ASUS-08 centralizes and verifies that unit against Payment, Refund, ledger, wallet, invoice, and PayTabs request/query contracts. All source snapshots and requested amounts must be exact multiples of the supported unit; reject unrepresentable amounts rather than silently round a customer refund. No binary floating point. If the provider uses another scale, precision or normalization remains a blocker and partial execution stays disabled. Other currencies need a separately verified unit; do not apply the JOD assumption to them.

## Status, access, and evidence policy

Each successful partial refund remains a distinct auditable `Refund` with its own idempotency key, status transitions, and `Status = InternallyRecorded`; never merge historical Refund records. Let `F` be the sum of successfully `InternallyRecorded` amounts after the current finalization. For `0 < F < Payment.Total`, set `Payment.Status = PartiallyRefunded`; for `F == Payment.Total`, set `Payment.Status = Refunded`; never commit `F > Payment.Total`. Preserve an append-only `PaymentStatusTransition` for each actual finalization: Paid → PartiallyRefunded, PartiallyRefunded → PartiallyRefunded for another partial, and PartiallyRefunded → Refunded for the last amount. Record the actual previous status, Refund correlation, actor/source, and idempotency key.

The partial refund is a **price concession only**. It does not end or shorten course access, delete Enrollment, revoke learning progress, or revoke completed results. It does not revoke an unused Included Evaluation Credit, recreate a consumed credit, or alter consumption. Academic history remains untouched. This preserves the approved P1 rule in `docs/decisions/refund-course-access-policy.md`. Full-refund access/credit policy stays separately governed by that decision.

## Provider, ledger, wallet, and document gates for ASUS-08

**Internal accounting capability:** Existing `PaidCourseSaleRefund` ledger event, Refund-linked `LedgerTransaction`, allocation-linked `LedgerEntry`, and signed Refund-linked `WalletTransaction` can carry one positive-revenue partial reversal per finalized Refund without schema changes. Book one balanced revenue-only transaction per Refund: debit PlatformCommission and TeacherEarningsPayable for the current share reversals, credit CourseSaleClearing for current course revenue reversals; omit zero entries. Book negative platform commission, teacher earning, or unassigned-course-revenue wallet transactions for only that Refund's share, grouped by `(RefundId, UserId, Type)`. Verify debits equal credits, each allocation/share's cumulative reversal remains within its original amount, and the whole sale is never over-reversed. Unique Refund ledger and wallet keys support idempotency, but ASUS-08 must enforce it transactionally. The current `BetccoDbContext.EnsureDoubleEntryLedgerIsBalancedAndAppendOnly` excludes a zero-revenue transaction, so ASUS-08 must reject that case or seek a separate approved design; no schema or guard change is proposed here.

**PayTabs execution capability:** `PayTabsPaymentProvider.CreateRefundAsync` can technically send `request.Amount` in `cart_amount`; `ToRefundTransaction` parses the returned amount and `RefundService.IsExpectedProviderTransaction` compares amount, currency, refund cart ID, profile, transaction type, and refund reference. `VerifyRefundAsync` queries by refund reference and uses the same comparison. Existing tests cover full-refund amount mismatch and query/timeout handling with a simulated provider, not partial requests, provider-side duplicate behavior, live partial settlement, or provider precision. The service's initiation gate and full-amount recovery checks still prohibit partial execution. **PAYTABS PARTIAL REFUND EXECUTION NOT ENABLED UNTIL ASUS-08 VERIFIES PROVIDER CONTRACT.** A method argument alone is insufficient evidence of production safety. ASUS-08 must verify create/query amount semantics, unique provider identity/idempotency after timeout, mismatch review, and test/live environment restrictions without blindly issuing another provider refund.

**Credit notes:** Current issuance accepts only a full-invoice amount. ASUS-08 must either safely extend internal `IssueCreditNoteAsync` so each finalized partial Refund may create its own partial `CreditNote` against the original Invoice, with cumulative note amounts capped by the Invoice, or keep partial credit-note issuance disabled until a separately approved slice. Multiple partial CreditNotes are not currently an operational capability. Statutory document requirements are separate.

## Concurrency, replay, and review stops for ASUS-08

Use PostgreSQL-authoritative serialization and/or row locking over the Payment/refund balance, with reload and bounded retry of recognized conflicts. Two simultaneous attempts must never finalize more than `Payment.Total`. Coordinate provider calls outside the local financial transaction without blindly repeating an uncertain request. Final financial effects and status transitions must be atomic, auditable, and idempotent **per Refund**. Replaying an `InternallyRecorded` Refund returns success with no additional ledger, wallet, credit, access, or document effects. Unresolved provider outcomes require reconciliation, not a second send.

Stop for review without committing partial effects when: Payment purpose is outside course/course-cart; Total/Tax/currency is invalid; requested amount is nonpositive, not representable, or above remaining balance; a prior external Refund may be pending; original allocations are absent, have mismatched currencies, nonpositive/invalid amounts, inconsistent total revenue, or inconsistent original split; previous Refund, tax, ledger, wallet, or transition evidence disagrees; cumulative rounding cannot reconcile; PayTabs amount/reference/profile/query evidence mismatches or is missing; or the partial credit-note path remains unresolved for a flow that requires a document. No schema, migration, runtime behavior, or tests are added in ASUS-07.
